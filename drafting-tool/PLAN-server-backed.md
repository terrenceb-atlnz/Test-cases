# Plan: Server-Backed Objective Drafting Tool (Restarted Iteration)

**Restart Note**: This iteration of the plan has been restarted per user direction. We are migrating away from the single-file static approach to a **server-backed architecture**. 

Key user feedback driving this:
- Will extend the tool beyond this iteration; does not mind difficulty to build.
- Will be self-hosted on local IP (likely behind nginx).
- Will never be offline.
- Current data is the *smallest* it will ever be (data growth expected).
- LLM integration is *necessary* to produce Objectives and Steps.
- Size is secondary (convenience for moving files locally).
- Iteration speed can benefit from LLM integration.
- **MAIN priorities**: 
  1. Repeatable *process* (enforced step-by-step workflow).
  2. Repeatable *outputs* (achieved via templating + structured processing of LLM responses for Objectives and Steps).

The plan now focuses on building a proper web application (backend + frontend) that fulfills the two main functions while strongly satisfying the updated constraints and main priorities. Previous single-file elements are migrated/adapted where useful (e.g. wizard logic, session model, process integration).

## Context

The existing "drafting tool" (generated by `tool/build_drafting_tool.py` producing `drafting-tool/index.html`) is a v1 single-file static HTML/JS app. It partially implements:

1. Use of the `OBJECTIVE_DRAFTING_PROCESS` (via wizard steps).
2. Producing standardized repeatable outputs (traceability.md + zephyr_payload.json + session).

**Significant gaps** in the current tool (confirmed via code and prior analysis):
- No native LLM support for synthesizing Objectives (declarative `<ul><li>` artefacts) and Steps (testScript) from user selections.
- Process doc not presented as an interactive web-based page.
- Data handling limited (partial embeds, File API not fully wired for full cross-references/exemplars).
- Drafting is manual only; no creation "based on the user's selections".
- Outputs have placeholders and are not fully templated for repeatability.
- No backend for direct LLM calls, data indexing, or enforced repeatable output generation.

**Project state**:
- ~41 cases processed to `refined-cases/` using the workflow.
- Three core databases: TestLink (historical via `testlink_awp.json` + candidates/decisions), Zephyr (via `zephyr_full/` + master), Enriched ATPyLib (via `test_id_description.json` + enriched suites).
- Strong existing logic for user review pauses, session provenance, export shapes, and the process principles.

**User directives for this server-backed restart**:
- Server-hosted (nginx reverse proxy to backend), local IP, never offline.
- LLM is required for generating Objectives and Steps (after review of the three DBs).
- Focus on repeatable process (strict step-by-step) + repeatable outputs (via prompt templating and LLM response processing/parsing).
- Tool can be complex to build; future extensibility is expected.
- Data will grow; server can handle indexing/loading.

This plan restarts the architecture to server-backed while migrating reusable concepts from the v1 (session/gating/export logic, process content, data access patterns).

## Recommended Approach

Build a **server-backed web application** (Python backend + web frontend) that:
- Runs persistently (e.g. uvicorn/FastAPI behind nginx).
- Loads and manages the (growing) data on the server.
- Enforces the repeatable step-by-step process with strong user-review gates.
- Uses LLM (directly from backend) to *create* Objectives and Steps from selections, with templating for repeatability.
- Presents the `OBJECTIVE_DRAFTING_PROCESS.md` as a first-class interactive web page.
- Produces standardized, repeatable file outputs.

**High-level architecture** (Python-centric to match project):
- **Backend**: FastAPI (async, excellent for APIs + docs, easy LLM integration). 
  - Startup: Load lightweight indices + efficient access to full data (e.g. in-memory for slim, streaming or pre-indexed for full zephyr jsonl, sqlite for search if needed).
  - Session management: Per-user sessions (UUID, stored in memory or lightweight DB like SQLite for persistence across restarts).
  - Step enforcement: Backend state machine for the 4-step process + confirms. Only allow synthesis after DB reviews confirmed.
  - LLM integration: Dedicated module with **prompt templates** (Jinja2 or similar files) for "generate objectives from selections" and "generate steps from objectives + selections". Call LLM (via litellm/openai-compatible for flexibility with Grok/Claude/etc.). Post-process responses with templates/parsers (e.g. extract `<ul>`, structured steps) to guarantee repeatable output format.
  - API: REST endpoints for wizard actions, selections, synthesis (LLM call), export.
  - Serve process doc: Render `OBJECTIVE_DRAFTING_PROCESS.md` (or sections) as interactive pages (markdown -> HTML), with deep links into the wizard steps.
  - File outputs: Generate `traceability.md`, `zephyr_payload.json`, and full session log using templates for consistency. Optionally write directly to `refined-cases/` or return for download.
- **Frontend**: Modern web UI served by backend (static files or templates).
  - Migrate/adapt the existing wizard UI (multi-step, tables for selections, confirms, objective editor, steps list).
  - Add "Process Reference" section/tab (interactive rendering of the doc).
  - Synthesis UI: "Synthesize with LLM" button (triggers backend templated call), view/edit result, "Apply to output" with validation.
  - Rich previews, search (powered by backend), review summary.
  - Use design tokens from `drafting-tool/design-tokens.css` for consistency.
  - Vanilla JS + lightweight framework (or plain fetch + HTML) to keep it maintainable; can evolve.
- **Hosting**: uvicorn/FastAPI app. nginx as reverse proxy (static config for local IP). No offline requirement.
- **Data strategy**: Server loads data at startup or lazily. Use efficient structures (pandas? or custom indexes for the three DBs). No browser size limits.
- **Repeatability**:
  - Process: Strict backend-enforced step order + confirmation state.
  - Outputs: Prompt templates + LLM + post-processing templates/validators ensure consistent shape every time (even if LLM varies slightly).
- **LLM**: Required for creation (after review). "Other means" still supported (manual edit or rule-based). Log full prompt/response for provenance.
- **Future extension**: Easy to add (more LLM features, better indexing, auth if needed later, richer process interactivity).

This directly addresses the two main functions and updated priorities. The single-file generator is deprecated in favor of a proper app (the generator pattern can be retired or kept for any static assets).

**Key benefits under user feedback**:
- Direct LLM necessary for Objectives/Steps.
- Server handles growing data.
- Templated repeatable outputs.
- Enforced repeatable process.
- Hosted behind nginx on local IP.
- Room to grow.

## Recommended Tech Stack (Python-first)
- Backend: FastAPI + Uvicorn + Jinja2 (for templates) + Pydantic (structured outputs).
- LLM: litellm or direct (openai-compatible endpoint) for flexibility. Prompt templates in `server/prompts/`.
- Data: Existing JSONs + optional SQLite for indexes/sessions.
- Frontend: Static HTML/JS (migrated from current wizard) + Tailwind or the project's design tokens. Served from `/static`.
- Other: python-dotenv for config (LLM keys), logging for audits.
- Deployment: Simple systemd/ or docker; nginx proxy_pass to backend.

No heavy JS framework unless needed later.

## Recommended Approach (Server-Backed - Restarted)

We are building a proper **server-backed web application**. The old single-file generator will be replaced (or repurposed for assets). The backend will handle data, LLM calls with templating, process enforcement, and output generation. Frontend will be a web UI (migrated/enhanced from current wizard) served by the backend.

See the architecture details and implementation outline below. The previous single-file-centric recommended approach, trade-offs, and pros/cons sections are superseded by this restart.

## Architecture Overview (Server-Backed)

- **Backend (FastAPI)**: Core logic, data loading/indexing, step state machine, LLM calls with prompt templates, output templating for repeatability, API.
- **Frontend**: Web UI (HTML/CSS/JS, migrated from current wizard + new Process page and synthesis features). Served statically or via templates.
- **LLM Layer**: Prompt templates (for repeatable inputs) + LLM call + structured parser / post-processor (for repeatable outputs).
- **Data Layer**: Server loads data (indices in RAM, full sources streamed or indexed).
- **Hosting**: uvicorn + nginx (reverse proxy on local IP). Persistent process.
- **Persistence**: Sessions (in-memory + optional SQLite/file dump for restart), generated artifacts written to `refined-cases/` or returned.
- **Repeatability**:
  - Process: Backend enforces wizard steps, confirmations, and "synthesis only after 3 DB reviews".
  - Outputs: Fixed templates for prompts + fixed templates/parsers for turning LLM text into exact `objective` + `testScript` + `traceability.md`.

This replaces the single-file generator approach.

## Critical Files to Modify / Create

**New server code (recommended structure)**:
- `server/main.py` — FastAPI app entry, lifespan for data loading, static mount.
- `server/routers/wizard.py` — Endpoints for load case, selections, confirm step, get state, synthesize (LLM), export.
- `server/llm.py` — Prompt template loading (Jinja), LLM client call, response parser to structured dicts (objectives list + steps list).
- `server/data.py` or `data_loader.py` — Load zephyr_master, candidates, decisions, slim_index, test_id, testlink on demand/full. Build searchable indexes.
- `server/templates/prompts/` — `generate_objectives.jinja`, `generate_steps.jinja` (include process principles + selections).
- `server/templates/outputs/` — Templates for traceability.md and perhaps payload assembly.
- `server/models.py` — Pydantic models for session state, selections, LLM request/response.
- `server/static/` — Frontend files (migrated index.html, JS for wizard, CSS using design tokens, Process guide page).
- `nginx.conf.example` — Sample reverse proxy config (proxy_pass to backend, static if needed).

**Modified / adapted**:
- `tool/build_drafting_tool.py` — Can be retired, or repurposed to generate the initial frontend static assets from the old template (migrate the wizard UI code).
- `drafting-tool/` — Contents (design tokens, style, process excerpts) can be moved into `server/static/` or `server/templates/`.
- `drafting-tool/README.md` → Update or move to `server/README.md` describing the new app, how to run, LLM config, nginx setup.
- Existing JS logic (session, gating, populate tables, confirm, export generation) migrated to frontend JS + backend enforcement.
- `OBJECTIVE_DRAFTING_PROCESS.md` — Used as source (read at runtime or build-time for serving as web page).

No changes (or minimal) to data files themselves, `refined-cases/`, upload tools, extract scripts.

## Implementation Outline (Mapped to Two Main Functions + Goals)

**Function 1: Use the OBJECTIVE_DRAFTING_PROCESS as a web-based page**
- Backend serves rendered / interactive version of the doc (markdown rendered to HTML with sections).
- "Process Reference" page/panel with:
  - Full or excerpted content.
  - Step anchors that highlight corresponding wizard state.
  - Interactive checklist synced with current session progress.
  - Quick reference cards extracted from the doc.
- Deep integration: From any step, "Show relevant process guidance" button.

**Function 2: Standardize the output of the process itself, in a repeatable process**
- Backend enforces step order and confirmation gates (state machine per session).
- Synthesis (Step 4, after 1-3 confirmed): 
  - Build prompt from template + all selections + case data + process excerpts.
  - Call LLM.
  - Parse + apply output template to produce structured objective + steps.
  - Auto-generate the required first traceability note step.
- Export: Use output templates to produce exactly formatted `traceability.md` and `zephyr_payload.json` (plus full provenance session log).
- All outputs validated against the shapes in the process doc and real `refined-cases/` examples.

**Goals coverage (updated for server)**:
- Size: No longer browser-bound. Data on server disk (can grow). Frontend bundle stays small.
- User-review forefront + streamline background: Backend enforces confirms before synthesis. Background (data indexing, prompt building, LLM call, templated output generation) is automatic.
- Create objectives and tasks based on selections (last): Backend LLM call with templated prompts (after review of three DBs). Supports "LLM or any other means".
- Objectives/Tasks last: Hard gate in backend state.
- Repeatable process: Step-by-step enforced.
- Repeatable outputs: Prompt templates + LLM + output templates/parsers.

**High-level changes**:
- New FastAPI backend handling data, state, LLM (with templates), exports.
- Migrate wizard UI logic to frontend that calls API.
- Add Process Reference UI.
- Add LLM synthesis with templating for repeatability.
- Add nginx hosting instructions.
- Deprecate or adapt old single-file generator.

**Logic to migrate/adapt**:
- Session model and provenance (key, selections, confirmed flags, timestamps, art, gaps, steps/objective): Adapt from `tool/build_drafting_tool.py` (JS) into backend Pydantic models + frontend state. Store on server.
- Gating + user review confirms (`canProceedToDraft`, confirm functions, "None" handling, nav status): Move enforcement to backend; frontend reflects state from API.
- Case selection + populate (Step 1 from candidates + decisions): Backend data layer + API.

- Objective preview + dynamic steps: Frontend (migrated).

- "Generated by..." + provenance footer: Include in generated outputs and session logs.

- Data recommendations: `data/zephyr_full/README.md`, `data/suites/suite_index.md`.

**Design**:
- Tokens: `drafting-tool/design-tokens.css` → serve in frontend.

The old single-file specific generator code will be retired in favor of the server app.

## Verification Section (End-to-End Testing)

After implementation:
1. Start the server (`uvicorn server.main:app --host 0.0.0.0 --port 8000`).
2. Access via nginx-proxied local IP (e.g. http://your-local-ip/tool or configured path).
3. Verify Process Reference page loads interactive content from `OBJECTIVE_DRAFTING_PROCESS.md`.
4. Select case, go through steps 1-3:
   - Selections, search, previews (powered by server data).
   - Explicit confirms.
   - Backend prevents progressing without confirms.
5. In Step 4 (after gate): Trigger "Synthesize with LLM".
   - Backend uses prompt template + selections.
   - LLM returns text.
   - Parser + templates produce structured objectives + steps (repeatable format).
   - User can edit + re-apply.
6. Export:
   - Produces perfectly formatted `traceability.md` + `zephyr_payload.json` (first step templated from selections).
   - Matches real examples + doc spec.
   - Session log captured.
7. Place output in `refined-cases/test/...` and validate.
8. Test repeatability: Same selections → same prompt template → consistent (templated) output structure.
9. Test data growth path: Load larger sets; server indexing works.
10. Regression: Existing cases' logic still produces correct artifacts when using manual path or LLM.

Success criteria: Tool enforces repeatable process, uses LLM for creation (after reviews), produces templated repeatable outputs, serves process as web page, runs behind nginx on local IP, ready for extension.
