## 1. Why

A case that finds out inside `main()` that it does not apply reports UNSUPPORTED the §3d way
(`self.supported = False`, then `self.failed()`). The framework then **power-cycles every device
on the bench** — about 4 minutes for tb470's six units, per case, per run. T33235 run 1 paid five
cycles for five fibre cases on a bench with no fibre link; run 4 paid one for TestCase_20. Every
script generated so far needed this fixed by hand before it could run cleanly, and the next one
will too, because nothing in the generator teaches it.

## 2. What the framework does (read from `/home/st-art/framework` on tb470, read-only, 2026-10-02)

| fact | where |
|---|---|
| The TestSet runs a case only `if testCase.supported or self.runUnsupported`, checked **per case, at its turn**. Without `-u`, a case whose `supported` is already False is not run at all: no configure, main or tear_down, no power cycle. | `ATTestSet.py` ~1755 |
| That covers **both** ways a case gets marked: the marking pass after `TestSet.configure()` (the declarative gates), **and** a mark an earlier case makes while running. | marking pass `ATTestSet.py` 1025–1210, called ~1680 after `configure()` |
| `skipIfExcl` matters **only under `-u`**: `TestCase.run()` then records `failed('Skipping TestCase methods because skipIfExcl is set')` without entering `__run()`, so the power cycle stays disarmed — UNSUPPORTED, no cycle. | `ATTestCase.py` 1063–1080 |
| A verdict reached inside `main()` costs the cycle: `__run()` re-arms `powerCycleOnFail = True`, and `run()` cycles on any non-PASS result. | `ATTestCase.py` 1075, 1083 |
| `testCasePlatformWithPropertyIncl = {'<dev attr on testSet>': [(['.*'], ['<prop>', …])]}` reads `getattr(dev, prop)` on the **device**; the case is supported if **any** listed property is truthy. | `ATTestSet.py` 975–1000, 1151–1170 |
| A case skipped either way writes **no** `<< …: RESULT` line and is not published. The marking pass logs `Test case N has been marked as unsupported on … without property …`; a mark made by another case logs only what the script logs. | T33234 run 3, `device-testing/IE520/port-2026-09-29/framework-run3-unsupported/test-9001.33234.log` lines 114–231 |

**Records this corrects (to fix when the work lands, not before):** the comments in T33234/T33235
and the messages of `d9a08dd`, `3454bc0`, `056114d` say `skipIfExcl` is what skips the case. In a
normal run the TestSet loop skips it; `skipIfExcl` only covers `-u` runs. The scripts are right —
keep `skipIfExcl = True` on every gated class so a `-u` run does not cycle either. The memory
`framework-unsupported-needs-a-failure` says "a fact found at runtime still needs the pair"; that is
true only for a fact the case finds **itself** (kind C). A fact an **earlier** case finds can be
marked before the later case runs (kind B).

### Kind C, worked example (for Terrence's decision, Q4)

TestCase_20 (step 21) builds an incompatible fixed pair: DUT test port `speed 100`, partner
`speed 10`. The DUT half is kind B — the sweep (TestCase_3) already asked the DUT about every
speed, and since `056114d` TestCase_3 marks TestCase_20 when the DUT refused 10 or 100. The
**partner** half is kind C: nothing before TestCase_20 asks the partner whether it takes
`speed 10`. On a bench where it does not, TestCase_20 is the first to find out, reports
UNSUPPORTED from `main()`, and the bench cycles.

Moving it forward would mean asking the partner earlier — e.g. `TestSet.configure()` sends
`speed 10` on `peer.portDut`, records accepted/refused on the partner device, restores the port,
and TestCase_20 carries a declarative gate on that property (it becomes kind A). What that costs:
1. **Layer.** `configure()` is SETUP, never a test (TEMPLATE-SPEC "three slot kinds"). A probe
   there records an answer without grading it, but it is still test-shaped work in the setup slot.
2. **Who decides a probe is needed.** If the generator invents it, the generator is making a test
   design decision. The alternative is Sequence Extraction proposing a `setup` probe step that
   Terrence sees and edits on the Sequence page.
3. **Every run pays the probe**, even on a bench where the case would run anyway (a few commands).
4. **The fallback stays**: state can change between probe and case, so TestCase_20 keeps its own
   check.
5. **`confCheck`**: the probe must restore the port before `configure()` returns, because the
   TestSet saves its config at the end of configure and compares each case's tear_down to it.

Payoff on T33235: **one** guard (the other kind-C-looking guards are anomaly guards). The payoff
could be larger in feature-probe cases (`show lldp` → `Invalid input`, the §3d example), which
none of the generated scripts has yet. Recommendation in the briefing: defer C until A and B are
built and the bench shows how often C fires.

## 4. Design — kind A (bench roles)

**Correction to the option (c) description given on 2026-10-02.** It said "the frame writes A
without the model, since it already knows the roles." The frame knows the roles the **case** needs
(`_detect_links`, text-driven, deliberately over-inclusive — safe only because an unused role
costs nothing). It does **not** know which **step** needs one. Stamping per-step gates from the
same text heuristics would make an over-inclusive guess skip a step that should have run — a lost
test, reported as UNSUPPORTED. So:

- **Frame (no model):** `TestSet.init()` sets one device property per optional role on the DUT
  switch handle, from discovery: `dut.has_fibre_link = self.fibre_supported`,
  `dut.has_cusfp_link = self.cusfp_supported` (names in Q3). It already computes both flags.
- **Model:** a case whose step needs a pluggable role carries
  `testCasePlatformWithPropertyIncl = {'dut': [(['.*'], ['has_fibre_link'])]}` and
  `skipIfExcl = True`, and keeps its in-`main()` check as the fallback. "Either link" is one tuple
  listing both properties (the framework's any-match).
- **Lint (BLOCKING, exact):** a `main()` that reports UNSUPPORTED on `fibre_supported` /
  `cusfp_supported` (or the None handles) without the matching class gate. The guard has a fixed
  shape on frame-owned names, so this check has no guesswork. A gate property counts when it is
  the frame's `has_<role>_link` **or** a property `TestSet.init()` assigns from that role's flag
  (T33235's hand-written `has_fibre_test_link`, `has_monitored_link`), so the hand-applied scripts
  read correctly.
- **Lint (WARNING):** a class gated on a role it never touches (no handle, port or flag of that
  role anywhere in the class) — an over-gated case is a lost test, reported as UNSUPPORTED.

Q1 asks whether the server should instead insert the gate itself when it sees the guard.

## 5. Design — kind B (an earlier case's result)

The sequence already carries the structure B needs: a producing step declares `publishes`
(`pt_extract_sequence.jinja`), the frame declares each as `self.<name> = None` in `TestSet.init()`,
and `_lint_published_unguarded` finds every case that reads one.

- **B1, frame + model + exact lint.** Frame helper `publish_value(testCase, name, value)` sets
  `testSet.<name>` and, when the value is None, marks every not-yet-run case that declares
  `ckNeeds = ['<name>', …]`, logging one fixed-format line per case. Model: the producer publishes
  through the helper; each consumer lists what it reads in `ckNeeds` and carries `skipIfExcl = True`.
  Lints (BLOCKING, exact — the reads are what `_lint_published_unguarded` already walks): the
  producing case never calls `publish_value(self, '<name>', …)` for a value it publishes; a case
  that reads a published value it does not list in `ckNeeds`; a `ckNeeds` entry nothing
  publishes; a `ckNeeds` class without `skipIfExcl = True`. (Not "no direct assignment": T33235
  builds `speedMap` across eleven cases with `self.testSet.speedMap.setdefault(...)`, a
  legitimate shape — §9 R1.)
- **B2, model + review.** `mark_cases_unsupported(testCase, caseNames, why)` moves from T33235 into
  the frame (same fixed-format log line). The producer calls it where a later step's condition
  fails. No exact lint is possible (the condition is free-form), so: a fill rule, a Review check
  ("a consumer gated on a published value's content — does its producer mark it?"), and a
  WARNING lint for a call naming a case that is not a later TestCase. **B2 lands through Review →
  Fix, not at generation:** a producer's unit prompt carries its own step, not the later steps'
  text where the condition is written (§9 R2).
- Every consumer keeps its in-`main()` guard: under `--include-test-cases` or run-priority
  sampling the producer may not run first, and then the guard is the only check.

## 6. Design — the result reader (D3)

`parse_framework_log` (`pt_exec.py:272`) counts only `<< …` blocks, so a correctly skipped case
makes the run read `status: short`. Read two more lines: the framework's
`Test case N has been marked as unsupported …` and the frame helpers' fixed-format line. A
registered case with no result block but a mark becomes `{result: "UNSUPPORTED", ran: false,
reason}`, and counts toward `ok`. The UI's run panel shows it as "not run — unsupported" with the
reason. Fixture: the T33234 run-3 log (14 cases dropped by the marking pass) and the T33235 run-4
log, trimmed and copied into `tests/`.

## 9. Review of this plan against the code (2026-10-02, before building)

- **R1 — no "direct assignment" ban.** T33235 builds the sweep's `speedMap` across TC 2–12 with
  `self.testSet.speedMap.setdefault(name, {})[value] = …`. Banning assignment outside the helper
  would reject it. The exact check is the converse: the producer must call `publish_value`.
- **R2 — B2 cannot happen at generation.** `pt_generate_step.jinja` gives a unit its own step,
  what it publishes and what earlier cases publish — never the later steps' text, which is where
  "only where the sweep recorded …" is written. B2 is therefore the Review's job (it sees every
  unit), and Fix applies it.
- **R3 — the frame knows roles per case, not per step** (§4), so the gate is model-written.
- **R4 — prompt and frame edits are live on save** (`llm.py` `Environment(FileSystemLoader(...))`,
  `auto_reload` default True). Hence the worktree build (§7).
- **R5 — blocking lints apply to existing sessions too.** T33234/T33235 already carry the gates
  (§4 accepts their property names) but not `ckNeeds`/`publish_value`, so a re-lint of T33235
  reports the B1 errors. That is accurate (the file predates the frame helpers); its file and
  session are left as they are, per the status header, and its bench runs go from the file.
- **R7 — found while building: contributors are not consumers.** T33235's stored sequence
  declares `speedMap` on steps 3–13; `_published_values` keeps the first, so the first lint draft
  demanded `ckNeeds` from ten steps that each ADD their own speed to the map — skipping them on a
  None would lose measurements they can still make. `_value_contributors` exempts a step that
  declares the value itself, and the unit prompt tells it so (`contributes_here`).
- **R8 — found while building: the Review taught the old shape.** Its "a suggestion must be code
  the static checks accept" list said `self.testSet.<name> = <value>`, pinned by G10's test; both
  now say `publish_value(...)` / `ckNeeds`.
- **R6 — no new reserved names needed.** `has_<role>_link` are device attributes and `ckNeeds` a
  class attribute; `_PUBLISH_RESERVED` guards TestSet attributes only.

**Known gaps, not built (each falls back to the in-`main()` guard, i.e. one cycle):**

  consumers are not marked;
- `--include-test-cases` runs still read `short` (the framework logs `Skipping TestCase N (not in
  --include-test-cases list)`; the reader does not count those as selected-out);
- kind C (deferred, Q4).
