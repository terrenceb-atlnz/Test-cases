# Sequence — AWPTCM-T44187

1. Over the console, configure base state on the DUT: enter Global Configuration, configure an IPv6 address with prefix on the management/transit interface connected to the test host (e.g. `interface <mgmt-if>` then `ipv6 address <ipv6-addr/prefix-length>`), create the test user accounts (a valid user, a second valid user for multi-session tests, and an account to be disabled later) with known passwords and the expected privilege level, and set `line vty 0 5` / `privilege level 15` as required.
   verify: Each command is accepted with no CLI error text, and `show running-config` on the DUT shows the configured IPv6 address on the management/transit interface and the created usernames.
2. Enable the SSH server on the DUT from Global Configuration (`service ssh` / `ssh server` enable form per the platform) and read the SSH server operational status with `show ssh server`. From the IPv6-capable test host, ping the DUT's global unicast IPv6 address and probe TCP port 22 on that address (e.g. a Scapy TCP SYN to port 22 over IPv6, or a socket connect).
   verify: `show ssh server` reports the SSH server as enabled and listening on the standard SSH port; the IPv6 ping to the DUT's global unicast address succeeds; the TCP probe to port 22 over IPv6 is answered (SYN-ACK / connect succeeds), proving an IPv6 listener is present.
3. From the test host, open an SSH session to the DUT using the DUT's GLOBAL UNICAST IPv6 address on the standard port with a valid username and password.
   verify: The TCP connection and SSH key exchange complete and the session reaches the DUT CLI prompt; the client reports no connection error.
4. From the test host, open an SSH session to the DUT's LINK-LOCAL IPv6 address on the management/transit interface, supplying the client-side scope/zone identifier (`fe80::.../%<host-if>`), with a valid username and password. Obtain the DUT link-local address first from `show ipv6 interface` output on the console.
   verify: The session establishes and reaches the DUT CLI prompt when the correct scope/zone identifier is supplied.
5. Where the platform supports SSH to a local loopback IPv6 address (configure an IPv6 address on the loopback interface and ensure it is routable from the test host), open an SSH session to that loopback IPv6 address.
   verify: Where supported, the session establishes and reaches the DUT CLI prompt; where the platform does not support a reachable IPv6 loopback destination, record the step as not-applicable rather than failing, and confirm the attempt is refused cleanly with the DUT still responsive.
6. Over the established IPv6 SSH session, authenticate with the valid username and password and issue a command that reports the current session privilege (e.g. `show privilege`) and a simple command such as `show system`.
   verify: Authentication succeeds, an interactive shell is granted, the prompt shown matches the expected exec prompt for the configured privilege level, and the issued commands return output with no authentication or authorisation error text.
7. Over the IPv6 SSH session issue a representative range of CLI commands including long/multi-line and paged output (e.g. `show running-config`, `show interface`, `show ipv6 interface`), capturing the full output. Issue the identical commands over an IPv4 SSH session (or the serial console) and capture that output.
   verify: The captured outputs are byte-equivalent apart from volatile fields (timestamps, uptime, counters, session/tty identifiers); no truncation mid-line, no corrupted or missing characters, and the last line of each long output is present in the IPv6-session capture.
8. With the SSH server enabled, establish an SSH session over IPv4 from one client and an SSH session over IPv6 from another client at the same time; issue commands alternately in each session (e.g. `show interface` in the IPv6 session, `show running-config` in the IPv4 session) and keep both open.
   verify: Both sessions authenticate and remain open simultaneously; each returns its own complete, correct output; neither session is dropped, stalled or mangled by activity in the other; `show ssh server` / active-session output lists both sessions with their respective IPv4 and IPv6 source addresses.
9. On the DUT, populate the SSH server's allowed-user configuration to permit the designated test users (`ssh server allow-users <username>` for each), then from the client attempt an IPv6 SSH login as each listed user in turn with the correct password.
   verify: Every user present in the allow list authenticates over IPv6 and reaches the CLI prompt; `show ssh server allow-users` (or the running-config SSH section) lists exactly the configured users.
10. On the DUT, add a user to the SSH server's deny-user configuration (`ssh server deny-users <username>`), then attempt an IPv6 SSH login as that explicitly denied user with the correct password.
   verify: The login attempt is rejected — the connection is refused or closed by the DUT without a CLI prompt being presented; no shell is granted; the console shows no new active session for that user.
11. Attempt an IPv6 SSH login as a username that is absent entirely from the SSH server allow-user configuration (and not a configured DUT user), using any password.
   verify: The attempt is rejected and the connection closed with no CLI access granted; the DUT remains responsive on the console and other sessions are unaffected.
12. Over IPv6, attempt SSH login as a VALID, allowed user supplying an INCORRECT password.
   verify: Authentication fails, the client is re-prompted or disconnected per configuration, no CLI prompt is ever presented, and no session appears in the DUT's active-session output for that attempt.
13. Over IPv6, attempt SSH login with an UNKNOWN username that exists nowhere in the DUT user database.
   verify: Authentication fails with no partial access — no shell, no prompt; the DUT does not reveal whether the user exists and the connection is closed cleanly.
14. Disable or expire one of the configured test accounts on the DUT (e.g. remove the username or apply the platform's account-disable form), then attempt an IPv6 SSH login as that disabled/expired account with its previously valid password.
   verify: The login is rejected and no CLI access is granted; the DUT logs the failure and remains responsive.
15. Repeat failed IPv6 SSH authentication attempts for a valid user beyond the configured retry limit to exercise any lockout behaviour, then wait for the configured lockout period to expire and attempt a login with the CORRECT password.
   verify: Attempts beyond the configured retry limit are refused/locked out as configured (no partial access at any point); after the lockout expires the correct-password login succeeds and reaches the CLI prompt, confirming recovery behaves as configured. Where the platform applies no lockout, record that the retries are simply refused and the correct-password login still succeeds.
16. Determine the configured maximum SSH session limit on the DUT (from `show ssh server` / running-config) and open that many concurrent IPv6 SSH sessions from multiple clients/users, issuing a distinct identifying command in each (e.g. `show users`).
   verify: All sessions up to the configured maximum authenticate and remain open simultaneously; each session returns its own correct output independently; the DUT's active-session output attributes each session to the correct username and source IPv6 address.
17. With the maximum number of IPv6 SSH sessions already established, attempt one further IPv6 SSH connection from the client, then issue a command in each pre-existing session.
   verify: The extra attempt is refused or queued according to the product design (connection closed/refused rather than granted a shell beyond the limit), and every pre-existing session still returns correct command output and remains usable.
18. With IPv6 sessions established, from the console/administrative session read the SSH server operational status and active session list (`show ssh server`, `show users` / active SSH session output).
   verify: The output reports the SSH server state as enabled, shows the address families being listened on including IPv6, and lists one entry per open session with a source IPv6 address, username and session identifier that match the sessions actually open (count and identities match the sessions the script opened).
19. From the administrative console session, terminate ONE of the active remote IPv6 SSH sessions by its session identifier as reported in the active-session list (e.g. the platform's clear/disconnect SSH session command), while other IPv6 and IPv4 sessions remain open.
   verify: The targeted client's SSH session closes immediately (client reports connection closed by remote host), that session identifier disappears from the DUT's active-session list, and every other session — IPv4 and IPv6 — still returns correct command output uninterrupted.
20. With IPv6 SSH sessions still active, disable the SSH server on the DUT from the console (the `no` form of the SSH server enable command). Then from the client probe TCP port 22 over IPv6 and attempt a fresh IPv6 SSH login, and issue a command in any still-open IPv6 session.
   verify: `show ssh server` reports the server as disabled; the TCP probe to port 22 over IPv6 receives no listener response (RST/refused); the fresh IPv6 SSH attempt is refused; existing sessions are handled deterministically per product design (dropped or left running, consistently on every repeat); the DUT console remains fully responsive with no exception trace.
21. Re-enable the SSH server on the DUT from the console WITHOUT restarting the device, then open a new IPv6 SSH session with a valid allowed user and issue a command.
   verify: `show ssh server` again reports the server enabled; the new IPv6 session establishes, authenticates and returns correct command output, confirming IPv6 connectivity is restored with no device restart.
22. From the client, attempt an IPv6 SSH connection to a MALFORMED or incomplete IPv6 destination address (e.g. `2001:db8:::1` / a truncated address).
   verify: The attempt is rejected cleanly at the client with an address parse/connect error and never reaches an authentication prompt; the DUT console shows no crash, exception trace or hang and `show ssh server` still reports the server enabled and serving.
23. From the client, attempt an IPv6 SSH connection to a syntactically valid but UNREACHABLE IPv6 destination address (an address not configured on the DUT and not routed).
   verify: The connection times out or is refused cleanly with no session established; the DUT remains stable and continues to serve existing and new IPv6 SSH sessions.
24. From the client, attempt an IPv6 SSH connection to the DUT's LINK-LOCAL address with the scope/zone identifier omitted, and again with a MISMATCHED zone identifier (a host interface on a different link).
   verify: Both attempts fail cleanly (invalid-argument/no-route/ unreachable at the client) with no session established and no partial authentication; the DUT shows no crash or exception trace and the correctly-scoped link-local login still succeeds afterwards.
25. From the client, attempt an IPv6 SSH connection to the DUT forcing an UNSUPPORTED cipher and then an UNSUPPORTED key exchange algorithm (client options selecting algorithms the DUT does not offer).
   verify: Each attempt fails during negotiation with a no-matching-cipher / no-matching-kex error and no session is established; the DUT remains stable, logs the failed negotiation, and a subsequent normal IPv6 SSH login still succeeds.
26. From the client, attempt an IPv6 SSH connection forcing an UNSUPPORTED SSH protocol version (e.g. force protocol 1 against a v2-only server).
   verify: The attempt is rejected cleanly at protocol-version exchange with no session established; the DUT console shows no crash, hang or exception trace and continues to accept valid IPv6 SSH sessions.
27. After exercising session establishment, successful and failed authentication, administrative session termination and SSH server enable/disable transitions, read the DUT log from the console (`show log`) and filter for SSH-related entries.
   verify: The log contains entries for IPv6 SSH session establishment, authentication success, authentication failure, the administrative session termination, and each SSH server enable and disable transition; each entry carries a plausible, monotonically increasing timestamp and, for session events, the correct source IPv6 address of the client.
28. With the SSH server enabled, the IPv6 listener active and the allow/deny user lists populated, save the configuration on the DUT (`copy running-config startup-config` / `write`), then restart the device and wait for it to boot. After boot, read `show ssh server`, the SSH allow/deny user configuration and `show ipv6 interface`, then attempt an IPv6 SSH login as an allowed user and as a denied user.
   verify: After restart the SSH server reports enabled, the management/transit interface still holds its IPv6 address, the allow and deny user lists match what was saved, the IPv6 TCP port 22 listener is present again, the allowed user logs in successfully over IPv6 and the denied user is still rejected — i.e. behaviour matches pre-restart.
29. Record baseline DUT resource usage from the console (`show memory`, `show users`, and the platform's process/file-descriptor or system status output), then run many repeated cycles (e.g. 100) of: open an IPv6 SSH session, authenticate (mixing valid logins with deliberately failed ones), execute a CLI command, and disconnect. Re-read the same resource outputs after the final cycle.
   verify: Every valid cycle establishes, authenticates and returns correct command output throughout the run (including the final cycles); failed authentications are rejected without granting access; after the last cycle the active-session list returns to its baseline (no orphaned sessions), memory and file-descriptor/process usage show no monotonic accumulation versus the baseline, `show log` contains no exception traces or crash records, and the DUT responds to CLI at normal speed.
