# Sequence — AWPTCM-T33233

1. Establish serial console sessions to the DUT and to the link partner switch, erase startup configuration on both and reload so each boots with no explicit port configuration, then wait for the CLI prompt to return.
   verify: Both devices return to the 'awplus#' prompt after reload and 'show running-config interface <port>' on the DUT shows no speed, duplex or polarity commands under the test port.
2. On the freshly started DUT with no port configuration applied, run 'show running-config interface <port>' and 'show interface <port>' for a copper test port and for a fibre test port taken from the [portlink] section of the .setup file.
   verify: No 'speed', 'duplex' or 'polarity' lines are present in the running configuration for either port, confirming auto-negotiation is the default administrative setting; 'show interface <port>' reports the operational result in prose ('current duplex ...', 'current speed ...', 'current polarity ...') separately from the configured setting, and 'show interface status' shows the negotiated values prefixed with 'a-' (e.g. 'a-full', 'a-1000') indicating auto negotiation. Where a media type is not present on the platform, that media is skipped and recorded as not applicable.
3. Prompt the operator to install a supported transceiver (from the SVT-agreed list) of the lower supported speed grade into the DUT fibre test port and the matching type into the partner fibre port, connected by fibre patch lead; then poll 'show interface <port> status' until the pluggable is detected and the port state changes.
   verify: Operator confirms insertion; 'show system pluggable' lists the inserted transceiver on the test port and 'show interface <port> status' transitions to 'connected'.
4. With both DUT and partner fibre ports left at their default auto-negotiation setting (no speed/duplex configured), read 'show interface <port>' and 'show interface status' on both ends.
   verify: 'show interface <port>' reports 'Link is UP' on both ends and the reported 'current speed' and 'current duplex' match each other and are consistent with the capability of the inserted transceiver type (e.g. a 1000 Mbps fibre SFP negotiates 1000/full); 'show interface status' shows the negotiated values with the auto 'a-' prefix.
5. Prompt the operator to remove the transceivers and insert a supported transceiver of a DIFFERENT speed grade (from the SVT-agreed list) in both DUT and partner fibre ports, then poll 'show interface <port> status' for the port to come back up.
   verify: Operator confirms; 'show system pluggable' reports the new transceiver type on the test port and 'show interface <port>' shows 'Link is UP' with 'current speed' matching the new transceiver's speed grade, demonstrating more than one supported speed grade is exercised.
6. Prompt the operator to connect the DUT copper test port to the partner copper port using a CROSSOVER copper cable, leaving both ports at default auto-negotiation, then poll 'show interface <port> status' until the port reports 'connected'.
   verify: Operator confirms cabling; the DUT copper test port reaches 'connected' in 'show interface <port> status'.
7. With the crossover copper auto/auto link up, read 'show interface <port>' on the DUT and 'show interface <partner port>' on the link partner and record the negotiated speed, duplex and polarity.
   verify: Both ends report 'Link is UP'; the prose 'current speed' and 'current duplex' values are identical on DUT and partner and equal the highest common capability of the two ports; the DUT reports a resolved polarity ('current polarity mdi' or 'current polarity mdix') with the configured polarity still auto.
8. Prompt the operator to replace the crossover cable with a STRAIGHT-THROUGH copper cable between the same two ports, then poll 'show interface <port> status' until the port reports 'connected'.
   verify: Operator confirms cable swap; the port returns to 'connected' without any configuration change.
9. With the straight-through copper auto/auto link up, read 'show interface <port>' on both ends and compare against the values recorded with crossover cabling.
   verify: 'Link is UP' on both ends; polarity is resolved automatically (the reported 'current polarity' is mdi or mdix, typically the opposite of the crossover case) while configured polarity remains auto; the reported 'current speed' and 'current duplex' are the same values reached with crossover cabling.
10. On the LINK PARTNER copper port only, restrict the advertised capabilities to a lower speed grade with 'interface <partner port>' then 'speed auto 100' (leaving duplex auto), and leave the DUT port untouched at auto. Wait for the link to re-establish.
   verify: DUT 'show interface <port>' reports 'Link is UP' with 'current speed 100' — the highest capability common to both ends — rather than the port maximum, and 'current duplex full'; 'show interface status' on the DUT shows the negotiated values with the 'a-' auto prefix.
11. Where the platform supports half duplex, further restrict the LINK PARTNER copper port to advertise only half duplex at a sub-gigabit rate with 'speed auto 100' plus 'duplex half' (half duplex is only valid at 10/100), leave the DUT at auto, and wait for the link to re-establish.
   verify: On platforms whose 'duplex' command accepts 'half', the DUT reports 'Link is UP' with 'current duplex half' and 'current speed 100', i.e. the highest common capability rather than the port maximum. On platforms where the duplex command offers only {auto|full}, the step is skipped and recorded as not applicable.
12. Remove the restrictions on the partner copper port ('no speed' and 'duplex auto' under 'interface <partner port>') to restore a full-capability auto/auto link, wait for the link to come up, and record the baseline negotiated speed, duplex and polarity from 'show interface <port>' on the DUT.
   verify: DUT reports 'Link is UP' with the original baseline 'current speed', 'current duplex' and 'current polarity' values recorded in the crossover/straight-through steps.
13. Force re-negotiation by cable: prompt the operator to unplug the copper cable from the DUT test port, wait for the port to report 'notconnect' in 'show interface <port> status', then reconnect it and wait for 'connected'.
   verify: Operator confirms; the port transitions to link down then back to 'connected', and 'show interface <port>' after reconnection reports the same 'current speed', 'current duplex' and 'current polarity' as the recorded baseline.
14. Force re-negotiation administratively: on the DUT enter 'interface <port>', issue 'shutdown', confirm link down, then issue 'no shutdown' and wait for the link to re-establish.
   verify: 'show interface <port>' shows the port administratively down then returns to 'Link is UP' after 'no shutdown', with 'current speed', 'current duplex' and 'current polarity' identical to the recorded baseline.
15. Force re-negotiation by device restart: save nothing (leave ports at default auto), issue 'reload' on the DUT, wait for the boot to complete and the console prompt to return, then re-read the test port state.
   verify: After reboot the DUT test port reaches 'Link is UP' / 'connected' without manual intervention and 'show interface <port>' reports the same 'current speed', 'current duplex' and 'current polarity' as the recorded baseline.
16. With the auto/auto copper link up and no change made on the DUT, change the LINK PARTNER's advertised capabilities to a different speed grade over its own CLI ('interface <partner port>' then 'speed auto 10', or another rate the port supports that differs from the current negotiated rate), and wait for re-negotiation.
   verify: Without any command entered on the DUT, DUT 'show interface <port>' updates to report the new highest common capability in 'current speed' (e.g. 'current speed 10') with matching 'current duplex', and the partner reports the same values; 'show running-config interface <port>' on the DUT still contains no speed or duplex configuration.
17. Restore the partner port to full auto advertisement ('no speed', 'duplex auto'), wait for re-negotiation, and re-read the DUT port state.
   verify: DUT 'current speed' and 'current duplex' return to the baseline highest common capability with no DUT configuration change, confirming the update is automatic in both directions.
18. Leave the DUT copper port on auto-negotiation (no speed/duplex configured) and FORCE the link partner to a fixed speed and duplex that MATCHES the DUT's maximum copper capability using the bare numeric forms on the partner, e.g. 'interface <partner port>' then 'speed 1000' and 'duplex full' (choosing a rate both ports support). Wait for the link to settle.
   verify: 'show interface <port>' on the DUT reports 'Link is UP' with 'current speed' equal to the partner's forced speed, and the resolved duplex reported in 'current duplex' consistent with the platform's documented fallback rules (typically full at that speed); 'show running-config interface <port>' on the DUT still shows no speed/duplex, proving the DUT resolved rather than was configured.
19. Keep the DUT port on auto-negotiation and change the link partner to a DIFFERENT fixed speed from the previous one, e.g. 'speed 100' with 'duplex full' on the partner port, and wait for the link to settle.
   verify: The DUT reports whatever it actually resolved in 'show interface <port>' — link up at 'current speed 100' with the duplex resolved per the platform's fallback rules (parallel detection commonly resolving half duplex where the platform supports half, full otherwise) — and the reported operational values match what the partner reports for speed. The check is that the reported operational values reflect the resolved result and follow the documented fallback rules for the platform, not a fixed speed/duplex pair.
20. Configure the two ends so they share no common capability: on the DUT copper port restrict advertisement to one rate with 'interface <port>' then 'speed auto 10', and force the partner to a different incompatible fixed rate with 'speed 1000' and 'duplex full' on the partner port. Leave the mismatch in place and poll 'show interface <port> status' repeatedly for at least a minute.
   verify: Either no link is established (the DUT port remains 'notconnect' in 'show interface <port> status' and 'show interface <port>' does not report 'Link is UP'), or a fault state is clearly reported by the platform; across the repeated polls the port state does not oscillate between up and down, and the interface counters show no repeated link-flap events in 'show log | include <port>'.
21. Remove the mismatch: issue 'no speed' (and 'duplex auto') on the DUT port and 'no speed' / 'duplex auto' on the partner port, then wait for the auto/auto link to re-establish.
   verify: Both ends return to 'Link is UP' at the baseline negotiated speed and duplex, confirming the mismatch condition was non-destructive.
22. On the fibre auto/auto link, prompt the operator to remove the currently inserted transceiver from the DUT fibre port; poll 'show interface <port> status' and 'show system pluggable' until removal is detected.
   verify: Operator confirms removal; 'show interface <port> status' transitions to 'notconnect' and 'show system pluggable' no longer lists a transceiver for that port, i.e. removal is reported in the port state.
23. Prompt the operator to insert a DIFFERENT supported transceiver type (different capabilities, from the SVT-agreed list) into the DUT fibre port and the matching type at the partner, leaving both ports at auto; poll until the port comes up.
   verify: 'show system pluggable' reports the new transceiver type; 'show interface <port>' reports 'Link is UP' with 'current speed' and 'current duplex' in line with the newly inserted transceiver's capabilities and matching the partner's reported values.
24. Prompt the operator to remove the second transceiver and re-insert the ORIGINAL transceiver type at both ends; poll until the port comes up.
   verify: 'show system pluggable' reports the original transceiver type again, insertion is reflected in the port state, and 'show interface <port>' reports 'Link is UP' with 'current speed'/'current duplex' back at the values negotiated for the original transceiver.
25. After the link-up, link-loss and re-negotiation events exercised above, collect the platform's records for the test ports: 'show log' filtered on the test port, 'show interface <port>', 'show interface status', 'show interface <port> status' and the interface counters from 'show interface <port>' / 'show platform port <port>' where available.
   verify: The log contains link up and link down entries for the test port matching each transition that was forced (cable removal, shutdown/no shutdown, reload, transceiver removal/insertion); the negotiated speed and duplex reported in the prose 'current speed'/'current duplex' of 'show interface <port>' agree with the 'a-' prefixed values shown in 'show interface status' for the same port, i.e. the negotiated values are reported identically across the available management paths.
26. Record baseline interface error counters and device resource usage on the DUT ('show interface <port>' counters, 'show memory', 'show cpu'), then cycle the COPPER link through negotiation repeatedly over a sustained run by issuing 'shutdown' / 'no shutdown' on the DUT copper port for a large number of iterations, reading 'show interface <port>' after each cycle.
   verify: On every iteration the link returns to 'Link is UP' with the same 'current speed', 'current duplex' and 'current polarity' as the baseline; between iterations the port does not report additional unexpected link transitions in 'show log'; interface error counters show no growth beyond baseline and 'show memory' / 'show cpu' do not trend upward across the run.
27. Repeat the sustained negotiation cycling on the FIBRE test port by issuing 'shutdown' / 'no shutdown' on the DUT fibre port for the same number of iterations, reading 'show interface <port>' after each cycle, and re-reading resource usage at the end.
   verify: Every cycle re-establishes 'Link is UP' with the same negotiated 'current speed' and 'current duplex' as the fibre baseline for the inserted transceiver; no unexpected flapping appears in 'show log', interface error counters do not grow, and 'show memory' / 'show cpu' show no upward trend across the run.
